# Plan: one web page for the window

**Goal:** replace the native session browser and the settings page with one
React page that the window hosts, at feature parity with today, looking like
a first-party Mac app ([ADR 0017](../adr/0017-one-web-page-for-the-window.md)).
**Architecture:** `ui/` becomes a React 19 + shadcn/ui + Tailwind v4 app built
by Vite into the single inlined `assets/settings.html` (the committed bundle
name stays, the CI drift check depends on it). The bridge is request/response
(`{id, method, params}` → `window.ambient.reply`) plus events
(`window.ambient.event`), routed in Rust through `api::call`. Each task leaves
the app working: settings first, then sessions and transcript, then the live
pane, then the host swap.
**Tech Stack:** React 19, shadcn/ui (components copied into
`ui/src/components/ui`), Tailwind v4 via `@tailwindcss/vite`, lucide-react,
vitest + `@testing-library/react` + jsdom, pnpm; Rust objc2 host.

## Global Constraints

- The bundle is one HTML file with everything inlined (`vite-plugin-singlefile`, `assetsInlineLimit: Infinity`, target `safari18`); nothing is fetched at runtime. Build output stays `assets/settings.html`.
- Every dependency is pinned to the exact version `pnpm add` resolves at task time and recorded in `ui/package.json`; the lockfile is committed; CI runs `pnpm install --frozen-lockfile`.
- Look: system font stack (`-apple-system, system-ui`), shadcn `neutral` base colour, `--radius` 0.5rem, HIG spacing (8 pt grid), light/dark from `prefers-color-scheme` (the `dark` class is set from a `matchMedia` listener, no toggle), sidebar uses the `sidebar` tokens. No custom display type.
- Tests run with `pnpm test` (`vitest run`) under node with jsdom; every component task adds tests that render the component with a fake bridge.
- The Rust bridge holds the state; the page keeps only what is on screen and re-requests after every `event`.
- This plan lands after the ui-api plan.
- No `.github/workflows/`, `.claude/`, or `loop/` changes; no editing existing tests. `uicheck` (`src/bin/uicheck.rs`) is a binary, not a test, and is updated in the task that changes what it drives.

**Interfaces:**
- Produces (page): `bridge.call<T>(method: string, params?: object): Promise<T>` posting
  `{"id": <n>, "method", "params"}` to `window.webkit.messageHandlers.ambient`, resolving when Rust
  calls `window.ambient.reply(id, {result} | {error: {kind, message}})`; `bridge.on(name, handler)`
  for `window.ambient.event(name, payload)`; a `FakeBridge` in `ui/src/test/fake-bridge.ts` that
  answers from a map for tests and can hold a reply until the test releases it. Stale replies: every
  screen that loads data for a selection keeps a generation counter, bumps it on each new selection,
  and drops a reply whose generation is not current (a `useLatest(call)` hook in `ui/src/lib/latest.ts`
  that all data-loading components use).
- Produces (Rust): `Bridge` routes every message to `api::call` with the real `Paths`, replying via
  `evaluateJavaScript("window.ambient.reply(<id>, <json>)")`; `Bridge::event(&self, name, payload)`,
  which queues the payload while the page has not yet called `init` and flushes the queue on `init`;
  the page calls `init` once on mount and receives `{route: "sessions"|"settings"}`, the route Rust
  holds in a `Cell` that `select_settings` sets (so a cold launch through Settings… lands on Settings
  whether the event or the page comes first); the old `Patch` path is deleted in Task 2, so this task
  keeps `handle` for messages without `id`.
